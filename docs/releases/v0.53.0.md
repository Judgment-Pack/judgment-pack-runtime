# v0.53.0

**The registry 1.1.0 reading joins the registry line.** From `v0.53.0`, the commands that
assemble a registry from several repositories, check its index, write and check its lock, sign a
lock and a source statement, and verify a lock's signatures are part of the registry line under
the promise in [VERSIONING.md](../../VERSIONING.md#the-registry-110-reading). This is the release
that section's "from the release that names it so in its release notes" refers to. `jpack` and the
runtime module stay `0.x`.

The reading follows registry format `1.1.0`, `spec/registry.md` together with
`spec/registry-1.1.0.md`, released on the spec tag `registry-v1.1.0` and not yet stable. Format
`1.0.0` and every command that reads it are unchanged.

## The registry 1.1.0 reading is part of the registry line

- **What it is.** `jpack registry assemble` and `jpack registry check-index` (the assembler and
  the index checker, with bounds a repository may only tighten); `jpack registry lock write`,
  `lock check` and `lock coverage` (the lock writer and the lock checker); `jpack registry lock
  sign`, `jpack registry source sign` and `jpack registry lock verify` (signing, the lock
  signature verifier and its serial record). Their flags, forms, defaults and exit codes; the
  formats under their `"1.1.0"` selectors; the 53 `FED-*` and `LOCK-*` codes, each an error; the
  serial record's form and its compare and set; and the bounds.
- **The promise.** The registry line's rules apply: within major version 1 of the line, nothing is
  removed, no bound is tightened, and a new refusal code, or a refusal of an input accepted
  before, is a breaking change. The documents the commands write are RFC 8785 canonical bytes, so
  a change to their bytes for the same inputs moves their selector.
- **Released, not stable.** The companion becomes stable when a second, independently written
  reader agrees on every row of a class. That changes nothing in this promise.
- **Not part of it.** The wording of messages; the readings
  [docs/registry-federation.md](../registry-federation.md#readings) lists where the text leaves a
  choice open; the Go packages; memory use and time.

## Upgrading

A project that pins `jpack` and does not use registry federation needs to do nothing: no command,
flag, output or exit code it uses changes.

A project that tried the federation commands while format `1.1.0` was proposed (`v0.53.0`
development builds only; no earlier release has them):

- **The rows changed after acceptance.** An emitter manifest given that the lock does not list,
  and any manifest given for a lock that names no emitters, is now `LOCK-EMITTER-MISMATCH` at
  `/emitters`. A signature document that admission refuses, such as one holding an integer above
  2^53 − 1, is `LOCK-SIG-DOCUMENT`, even when it also has a member that is not defined.
- **`lock verify` opens only the documents it reads.** A `--signature` or `--source-signature`
  document beyond the lock's sources count plus one is `LOCK-SIG-EXTRA` and is never opened, so a
  path there that does not exist is reported, not an input error.
- **Keys and seeds.** For `lock sign` and `source sign`, `--key` names a seed file, and no flag
  takes a seed inline. `--public-key` is required, and a seed whose public key is another is
  refused before anything is signed. Neither may name a remote path. `lock write` takes the
  standard owner's public key as `--standard-public-key` (it was `--key`, which is now no flag of
  `lock write`); it and the `--public-key` flags take public keys, never a seed.
- **The serial record.** `--record-dir` has no default. With no record for the registry id,
  `--floor` must be given; `--floor 1` accepts whatever lock comes first. A lock file left beside
  a record is never removed by the runtime: remove it once no verifier is running.

## For an unchanged pack

For every supported `specVersion` (`0.5.0`, `0.3.0`, `0.2.0-draft`, `0.1.0-draft`), no
disposition, evaluation output, decision record byte or digest differs from `v0.52.0`.

Comparing the `v0.52.0` release binary with this release's build:

- **Conformance runs.** For each selector, with and without `--strict`, `spec test-conformance
  --format json` gave the same bytes and the same exit code, apart from the tool's version.
- **The evaluation corpora.** For `0.2.0-draft`, `0.3.0` and `0.5.0` (20, 20 and 103 cases),
  `experimental evaluate-corpus --format json` gave the same bytes apart from the tool's version.
- **Spec validation.** On each of the 2757 JSON files Spec `v0.6.0` tracks, `spec validate` gave
  the same exit code and the same output.
- **The reference emitters.** `jpack emit conformance` over the vectors of `jpack-emit-go-facts`
  and `jpack-emit-ts-constants` gave the same report and exit code (59 and 101 rows, every one
  passing or skipped).
- **`jpack terraform facts`.** Over each of the companion's vectors whose declaration a command
  line can write, 175 runs, the exit code, standard output and standard error were the same bytes.

## What is new

- **Every class of registry format 1.1.0 is built** (`internal/federation`, `internal/regsig`):
  assembly, the assembled index and its check, bounds, the lock, its writer, check and coverage,
  the signature documents, signing, verification and the serial record.
- **The companion's rows run in the tests, pinned to the release tag.** The 162 hand-written rows
  of `registry-v1.1.0` are vendored unmodified under `internal/federation/testdata`, pinned by
  Spec revision and each file's SHA-256. Every row of every class runs in the package and through
  the commands, with the result the companion's second reader gives; that reader is by the same
  vendor, so this is not a cross-vendor claim. The pin is the commit the tag names, `5f95fe86`.
- **Fuzz targets** for the manifest, bounds, the index, assembly, the lock and its check, the
  signature documents, the serial record and verification.
- **The mutation table** has a row for every `FED-*` and `LOCK-*` code, each with the test that
  kills its recorded mutant (docs/registry-mutation-table.md).

## Known limits

- **Windows.** The serial record's and its directory's permissions are not checked, and the
  directory is not synced: a power loss just after a record is written may leave the record as it
  was. A floor no lower than the last serial accepted covers that. No key signs on Windows.
- **The record's owner** is not checked, only its group and other write bits.
- **A lock file that cannot be removed** after a successful write is reported, and the lock is not
  accepted, although its record is written; verifying the same lock again accepts it as already
  recorded.
